MPS vs CPU for LeRobot ACT Inference

A short explanation of why your ACT policy behaves differently on Apple MPS and CPU, using the timing logs from your SO-101 rollout.

CPU chunk refill timing ~190-245 ms

CPU was steady, but each ACT chunk refill stayed around 4-5 Hz.

MPS after warmup ~47-55 ms

MPS had a slow first refill, then much faster follow-up refill ticks.

Bottom Line

For your ACT model, MPS is the better runtime after it warms up. CPU inference stayed near ~250 ms per chunk refill, while MPS dropped to about ~50 ms on later chunk refills when device synchronization timing was disabled.

Use --policy.device=mps for this rollout. Keep LEROBOT_ROLLOUT_TIMING_SYNC_DEVICE=0 unless you specifically need synchronized stage-level profiling.

What CPU Mode Does

CPU mode runs PyTorch tensor operations on the Mac CPU cores. It has simple timing behavior: the operation usually finishes before Python continues, so profiler numbers are easier to read.

In your CPU run, almost all time was spent in ACT's model call: 

loop.total ~= 248 ms
inference.policy_select_action ~= 243 ms
robot.get_observation ~= 1 ms
robot.send_action ~= 0.1 ms

This says the cameras and robot serial command path were fine. The CPU bottleneck was model inference.

What MPS Mode Does

MPS is Apple's Metal Performance Shaders backend for PyTorch. It moves eligible tensor operations to the Apple GPU through Metal. That can accelerate neural network operations, especially convolution and transformer work, but it behaves differently from CPU execution.

  • MPS has one-time setup and kernel warmup costs.
  • MPS execution is more asynchronous than CPU execution.
  • Some operations may still run on CPU or require CPU/GPU data movement.
  • Fine-grained timing can look misleading unless the device is synchronized.

Your MPS run showed this pattern: 

first refill tick ~= 240 ms
later refill ticks ~= 47-55 ms

That is normal: the first call pays warmup/setup costs; later calls reuse initialized kernels and cached execution paths.

Why Stage Timings Look Odd on MPS

With LEROBOT_ROLLOUT_TIMING_SYNC_DEVICE=0, Python does not force MPS to finish every GPU operation before recording each stage time. This reduces profiling overhead and better reflects control-loop performance, but individual stage numbers can shift.

For example, your MPS log showed values like: 

inference.policy_select_action ~= 15 ms
inference.postprocessor ~= 25-35 ms

That does not necessarily mean the postprocessor is truly the expensive operation. Some GPU work launched during policy_select_action may only become visible later when another operation forces synchronization.

For MPS, trust loop.total for control performance. Treat per-stage timings as approximate unless LEROBOT_ROLLOUT_TIMING_SYNC_DEVICE=1.

ACT Chunk Caching

ACT predicts a chunk of future actions, then returns cached actions for later control ticks. With n_action_steps=25 and fps=25, the model should run roughly once per second. 

tick 1:  run ACT model, create 25 actions
ticks 2-25: use cached actions
tick 26: run ACT model again

This is why occasional slow-loop warnings are acceptable. The warning marks the chunk refill tick, not necessarily every control tick.

Recommended Run Settings

For normal use after debugging: 

LEROBOT_ROLLOUT_TIMING=0 \
LEROBOT_ROLLOUT_TIMING_SYNC_DEVICE=0 \
lerobot-rollout \
  --policy.device=mps \
  --fps=25

For occasional diagnostics with low overhead: 

LEROBOT_ROLLOUT_TIMING=1 \
LEROBOT_ROLLOUT_TIMING_SYNC_DEVICE=0 \
lerobot-rollout \
  --policy.device=mps \
  --fps=25

For more accurate MPS stage attribution, at the cost of overhead: 

LEROBOT_ROLLOUT_TIMING=1 \
LEROBOT_ROLLOUT_TIMING_SYNC_DEVICE=1 \
lerobot-rollout \
  --policy.device=mps \
  --fps=25

Interpreting Warnings

At fps=25, the loop budget is only 40 ms. If an MPS chunk refill takes 50 ms, it will still produce a warning even though it is close to the target. That is much better than the CPU refill path at ~250 ms.

A warning once per action chunk is usually acceptable. A warning on every control tick means the action cache is not being used or the policy is being reset too often.
